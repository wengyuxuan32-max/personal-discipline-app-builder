# Android 实现与验收

只在用户确认完整规格并明确要求开始制作后读取本文件。

## 实现选择

- 根据已选功能、离线需求、设备范围和长期维护选择架构；原生 Android 通常优先考虑 Kotlin、Jetpack Compose、Room、DataStore、WorkManager、AlarmManager 和系统通知。
- 数据保存方式必须遵循用户选择，不能擅自把纯本地改成联网，也不能因实现方便删除用户已选功能。
- 根据当前用户手机确定重点测试机型，同时覆盖规格中声明的 Android 版本范围；不得把一位用户的设备写成通用默认值。
- 只有选择强闹钟时，才实现并说明通知、精确闹钟、全屏提醒、锁屏和厂商后台限制。
- 只有选择账号、同步、协作或联网 AI 时，才引入服务器和相关依赖，并再次确认费用与隐私。

## 结构与可持续升级

- 按功能边界组织界面、业务、数据和系统能力，避免把全部逻辑堆在单个页面或文件中。
- 固定 application ID，并保持正式签名密钥不变。
- 每次交付提高 `versionCode`，让新版可覆盖安装。
- 数据表或字段变化必须提高数据库版本并提供显式迁移；不得用破坏性迁移掩盖问题。
- 备份格式带版本并兼容旧字段缺失；覆盖安装后不要求用户重新导入数据。
- 不把签名密码、真实备份或其他敏感信息提交到公开仓库或打包进 APK。

## 功能实现检查

对每个已选模块逐项核对：

1. 常见手机宽度和大字体下入口可见、可点击。
2. 新增页面或弹窗能打开，输入控件可获得焦点。
3. 软键盘不遮挡关键字段和保存按钮。
4. 必填校验、保存、立即显示和重启后的持久化正确。
5. 编辑、完成、撤销、恢复、归档和删除符合规格。
6. 空数据、重复、误操作、过期和权限关闭有合理反馈。
7. 导航调整后重新检查所有新增、编辑、保存和删除入口。

不要把带有 `fillMaxWidth()` 等占满宽度行为的组件错误并排，导致输入框或按钮被挤出屏幕。

## 数据与业务验证

- 为周期、日期边界、评分、统计、建议、备份兼容和数据库迁移编写与实际选择相匹配的测试。
- 运行单元测试、Lint 和 release 构建。
- 对图表检查小屏、大字体、长分类名、极端数值和空数据，避免图形与文字重叠。
- 对提醒检查应用关闭、锁屏、手机重启、权限拒绝和时区变化。
- 对导入检查合并、覆盖、重复数据、旧格式和失败回滚。
- 没有真机或模拟器验证时必须明确说明，不能把编译成功描述成“已完全实测”。

## 交付

根据用户要求交付：

- 使用同一正式签名的 release APK。
- 可继续开发的完整源码。
- 安装、权限、备份、换机和覆盖更新说明。
- APK 与源码包校验值。
- 签名证书摘要和最低、目标 Android 版本。

提醒用户覆盖安装前先备份；如果目标是保留旧数据，不要先卸载旧版应用。
